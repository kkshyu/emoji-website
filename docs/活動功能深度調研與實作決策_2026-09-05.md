# 官網活動功能深度調研與實作決策

- 對象：emoji／台灣人才聚落官網產品與營運團隊
- 日期：2026-09-05
- 範圍：參考 Luma 現行公開文件，判定官網第一版活動模組的功能、付款、簽到與管理邊界
- 假設：沿用現有 Express、Postgres、Google 登入、Stripe Checkout、管理員權限與 QR 簽章；活動以台灣實體活動、單一 TWD 票價為主
- 排除：不複製 Luma 的社群探索平台、原生 App、Wallet Pass、多人／多票種、折扣碼、候補與審核式延後扣款

## 直接結論

不需要另建活動 SaaS 或前端框架。現有系統已有 `events`、`event_regs`、Google 登入、Stripe 與 HMAC QR，最小完整做法是擴充現有資料表及 API，新增同站活動列表／詳情頁，並把管理、付款核銷、退款、名單、QR 與人工簽到放回既有 `/admin` 和會員登入流程。

第一版的完整驗收主線：

1. 管理員可建立公開或私人活動，設定時間、地點、名額、免費／固定 TWD 票價與發布狀態。
2. 公開活動出現在 `/events`；私人活動不出現在清單，但持直接連結者可以查看。
3. 使用者登入後報名；免費票立即成立，付費票導向 Stripe Checkout。
4. 付費票只在 Stripe 簽章 webhook 或付款後伺服器查證成功時成立，兩條路共用同一個冪等核銷函式。
5. 成立的報名產生簽章 QR；後台可掃碼或由名單人工簽到、取消簽到、匯出 CSV，付費票可由後台全額退款。

## Luma 現行能力與本案取捨

| 能力 | Luma 證據 | 本案決策 | 信心／限制 |
|---|---|---|---|
| 公開／私人可見性 | Luma 將 Public 定義為可列出及索引；Private 是不列出、持連結者可報名 | 第一版同義實作：public 列表、private unlisted direct link | 高；私人不是密碼或邀請名單 ACL |
| 會員限定 | Luma 另有 Member-Only，與 Private 不同 | 不做；需求只指定公開／私人 | 高 |
| 固定票價與 Stripe | Luma 連接 Stripe、票價固定幣別，顯示全額價格 | 第一版單一票種、免費或固定 TWD | 高；多票種與彈性定價延後 |
| 票種／銷售窗／審核／候補 | Luma 將這些放在 ticket type 層，既有報名條件不因後續改價而變 | 第一版只保存每筆報名的應付金額快照；不做 ticket type 子系統 | 高；需求擴大時再加表，不預建抽象 |
| 付款核銷 | Stripe 要求 webhook，且核銷必須能重複、併發呼叫而只執行一次；成功頁只能補快，不可取代 webhook | `checkout.session.completed` 與 `async_payment_succeeded` 共用冪等核銷；付款回站再補查 | 高；部署必須設定 webhook secret |
| 退款 | Luma 後台可全額或部分退款，並可使票券失效 | 第一版後台只做全額退款並立即失效票券 | 高；部分退款、手動 Stripe 後台同步延後 |
| 簽到 | Luma 每位來賓有 QR，也能以姓名／email 人工查找；Standard 模式可確認與復原，Express 掃描即簽到 | 第一版 QR 掃描即簽到、名單按鈕人工簽到、可取消簽到 | 高；專用 check-in staff 權限延後 |
| 名單 | Luma 可依狀態搜尋／篩選並匯出含付款、票種、簽到時間的 CSV | 第一版沿用單場名單，新增付款／簽到欄與 CSV | 高 |
| 通知、日曆、問卷、分析 | Luma 提供確認信、提醒、Blasts、日曆邀請、問題欄位及漏斗／來源分析 | 不在第一版；現有系統沒有寄信／行事曆基礎，加入會擴大營運與個資範圍 | 高 |

## 現況差距

| 流程 | 現況 | 缺口 | 第一版修正 |
|---|---|---|---|
| 活動發布 | `events` 只有標題、時間、地點、名額、狀態 | 無公開頁、私人連結、結束時間、價格 | 擴欄＋`/events` 列表／詳情 |
| 報名 | 登入會員可免費報名，`event_regs` 只有 note | 無付款狀態與金額快照 | registration 狀態、應付／已付、Stripe session |
| 容量 | 先 count 再 insert，未鎖列 | 併發可能超額 | 活動列鎖＋有效 pending 保留名額 |
| 付款 | 只有會籍與點數 Checkout | 活動無 webhook 核銷 | 活動專用 metadata、webhook、成功頁補查 |
| 退票 | 刪除報名 | 已付款紀錄可能錯失 | 免費可取消；付費只由後台退款 |
| 簽到 | 只有空間門禁短效 QR | 活動票券與出席資料不存在 | 活動票簽章、DB 狀態交叉驗證、簽到時間 |
| 後台 | 可建／改／刪活動、看基本名單 | 無可見性、票價、付款、退款、簽到 | 原活動分頁原地擴充 |

## 安全、法遵與營運邊界

- 付款成立不得相信前端 query string；Stripe 明確要求用 webhook 保證核銷，成功頁查證只處理使用者立即看到票券的體驗。
- 活動 QR 只攜帶簽章識別資料；簽到時仍查資料庫確認活動、報名狀態與是否退款，避免已退款票券繼續可用。
- 報名名單包含姓名、email、電話、付款與出席資訊，只供管理員。法務部個資法第 8 條要求直接蒐集時告知蒐集者、目的、類別、利用期間／地區／對象／方式、權利及不提供的影響；正式收單前應由營運確認既有隱私告知是否涵蓋活動報名。
- Stripe 收據不是台灣統一發票。財政部電子發票規範把網路銷售貨物或勞務所開立、傳輸或接收的統一發票納入電子發票；本次不虛構發票串接，正式收費活動上線前應確認開票主體及既有電子發票流程。
- 管理員刪除有報名的活動會破壞付款與簽到稽核，因此第一版改為禁止刪除已有報名的活動，改用「已結束」。

## 實作與驗證結果

- 已完成前台三語活動清單／詳情、公開與私人直連、免費報名、Stripe Checkout、付款回站查證、簽章 QR 票券及會員活動入口。
- 已完成後台活動欄位、名單與付款狀態、CSV、QR／人工簽到、重複簽到提示、取消簽到及付費票全額退款。
- 自動測試共 204 項全數通過，另以暫時 PostgreSQL 實測資料庫 migration、公開清單排除私人活動、私人直連、免費報名、QR、簽到冪等、取消簽到、取消報名後票券失效，以及有報名紀錄禁止刪除。
- 在 390×844 手機 viewport 實測公開清單與私人詳情，文件寬度等於 viewport、無水平溢位，瀏覽器 console 無 error 或 warning。
- 未使用正式 Stripe 金鑰進行真實扣款／退款；目前在缺少 `STRIPE_SECRET_KEY` 或 `STRIPE_WEBHOOK_SECRET` 時會拒絕建立付費報名，不會把未核銷付款誤判為成立。部署後仍須用 Stripe test mode 完成一次 Checkout、簽章 webhook、退款及重送 webhook 驗收。

## 研究停止條件

已取得每項第一版關鍵主張的一手來源，Luma 與 Stripe 對公開／私人、付款核銷及簽到流程沒有實質矛盾；個資與電子發票只影響上線前營運決策，不改變本次資料模型。繼續搜尋多票種、Wallet Pass、推播與 Discover 細節不會改變第一版實作，因此停止擴張。
